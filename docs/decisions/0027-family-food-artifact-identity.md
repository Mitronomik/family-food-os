# ADR 0027 — FamilyFoodOS artifact identity

## Status

**ACCEPTED FOR PR1 — NORMATIVE ONLY WHEN PR1 IS MERGED TO `main`**

Date: `2026-08-31`

## Context

FamilyFoodOS is a separate product fork bootstrapped from CosmeticWorkshopOS.
ADR 0025 established its current runtime and workspace identity, and ADR 0026
established the strict identity boundary for Restore. Current file-backed
artifacts must likewise identify FamilyFoodOS without deleting or silently
adopting historical CosmeticWorkshopOS files.

The inherited JSON export format contains two product-identity surfaces: the
manifest source and the strict generated filename marker. Its payload structure
and `export_schema_version = 1` contract do not otherwise change. Backup naming
is different: its existing grammar is intentionally generic and derives a safe
source stem from the configured database filename.

Strict generation and verification are trust boundaries. Best-effort artifact
listing is a historical visibility feature. Treating those two boundaries as
equivalent would either make legacy files disappear or incorrectly promote them
to current FamilyFoodOS artifacts.

## Decision

New FamilyFoodOS JSON exports use:

- `manifest.source = family-food-os`;
- `{timestamp}-family_food-export-{canonical_reason}[-N].json`.

`EXPORT_SCHEMA_VERSION` remains `1` because the JSON payload structure is
unchanged. A product-identity change alone does not define a new structural
schema.

The strict “generated by this current application” filename parser accepts only
the FamilyFoodOS `-family_food-export-` marker. A filename using the inherited
`-cosmetic_workshop-export-` marker is not a current generated FamilyFoodOS
filename, even when every other segment is structurally valid.

Verification of an application-owned current export requires
`manifest.source = family-food-os` in addition to all existing filename,
structure, schema, count, path and security checks. A CosmeticWorkshopOS source
is rejected rather than treated as equivalent merely because its JSON structure
is compatible. Verification never converts or rewrites the file.

Existing best-effort export and backup listing may continue to surface legacy
CosmeticWorkshopOS filenames where the established listing contract intentionally
shows historical files. Visibility does not imply trust, verification,
importability or compatibility.

Backup filename generation and parsing remain generic and stem-based. With the
current default database `family_food.sqlite`, a new default backup naturally
uses `{timestamp}-family_food-{reason}[-N].sqlite`. A custom database filename
continues to produce its own sanitized source stem. Backup filenames are not
product-identity proof and Restore continues to use the database-content rule
from ADR 0026.

No existing legacy artifact is deleted, moved, renamed or rewritten. Import or
migration of CosmeticWorkshopOS exports into FamilyFoodOS is not authorized by
this decision.

## Considered alternatives

1. **Keep the old CosmeticWorkshopOS artifact identity.** Rejected because new
   files from a separate product would claim the source product's identity.
2. **Accept both product sources as equivalent.** Rejected because structural
   similarity does not authorize cross-product trust or import compatibility.
3. **Bump the export schema version solely because product identity changed.**
   Rejected because the payload structure is unchanged and schema version must
   describe structure rather than branding.
4. **Use FamilyFoodOS identity for new artifacts while preserving legacy
   listing.** Selected because it establishes a strict current-product trust
   boundary without erasing historical visibility.

## Consequences

- Newly generated and verified exports identify FamilyFoodOS consistently in
  both contents and strict filenames.
- CosmeticWorkshopOS exports remain ordinary historical files where best-effort
  listing exposes them, but they are not current generated or verified
  FamilyFoodOS exports.
- Export schema consumers see no structural version bump.
- Default backup names naturally use `family_food`, while custom database stems
  and the generic parser remain supported.
- Neither export nor backup filenames become proof of Restore/product identity.
- Supporting cross-product import requires a separate explicit decision and
  implementation.

## Scope and supersession

This ADR becomes normative only when PR1 is merged to `main`.

It supersedes only current artifact-identity assumptions inherited from
CosmeticWorkshopOS. It does not rewrite legacy artifacts or older ADRs, change
the export payload structure, authorize import compatibility, alter Restore,
change migrations, or reopen artifact audit, transactional backup, listing or
security semantics beyond the current identity checks described here.
