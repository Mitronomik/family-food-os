# FamilyFoodOS
## Автоматическая загрузка и поддержание каталога продуктов, рецептов и меню

**Версия:** 0.1
**Статус:** дополнительное ТЗ к FamilyFoodOS MVP
**Связанный документ:** `technical-spec.md`
**Предполагаемое имя файла:** `data-ingestion.md`

---

# 1. Назначение документа

Настоящий документ описывает архитектуру и процессы автоматического наполнения FamilyFoodOS данными о:

- базовых пищевых ингредиентах;
- продуктах питания;
- конкретных товарах магазинов;
- упаковках;
- ценах;
- наличии;
- пищевой ценности;
- рецептах;
- меню;
- взаимосвязях между рецептами, ингредиентами и магазинными SKU.

Ключевая цель:

> **пользователь FamilyFoodOS не должен вручную создавать каталог продуктов и рецептов.**

Система должна максимально самостоятельно:

1. получать данные;
2. очищать их;
3. нормализовывать;
4. сопоставлять;
5. проверять;
6. обновлять;
7. формировать доступный пользователю каталог.

Человек должен вмешиваться преимущественно в исключительных случаях, когда система не способна принять решение с достаточной уверенностью.

---

# 2. Основной UX-принцип

Используется подход:

# Zero-entry first

Если информацию возможно получить автоматически, пользователь не должен вводить её вручную.

Предпочтительный порядок взаимодействия:

**автоматически определить → предложить → пользователь при необходимости исправляет**

вместо:

**пользователь вводит → система сохраняет.**

---

# 3. Что пользователь НЕ должен делать

Обычный пользователь не должен:

- вручную создавать продукты;
- вводить КБЖУ каждого продукта;
- указывать калорийность;
- указывать категории товаров;
- вводить цену каждого продукта;
- вручную переписывать состав упаковки;
- вручную связывать продукт магазина с ингредиентом;
- создавать базовые рецепты;
- вручную рассчитывать количество ингредиентов;
- искать соответствие рецепта и магазинных продуктов;
- обновлять цены;
- отслеживать изменение ассортимента магазина.

Все перечисленные процессы должны происходить централизованно.

---

# 4. Что пользователь может вводить

Ручной ввод оставляется только для персональной информации.

Например:

- состав семьи;
- вкусовые предпочтения;
- исключённые продукты;
- бюджет;
- любимые магазины;
- продукты, уже имеющиеся дома;
- оценка блюда;
- изменение планов на конкретный день.

Даже эти операции по возможности должны выполняться через:

- autocomplete;
- готовые варианты;
- checkbox;
- swipe;
- быстрые кнопки;
- natural language input.

---

# 5. Архитектурные уровни данных

Каталог должен иметь минимум четыре уровня.

```text
Canonical Ingredient
        ↓
Food Product Type
        ↓
Retail SKU
        ↓
Price / Availability Snapshot
```

Дополнительно над ними существует:

```text
Recipe
        ↓
Recipe Ingredient
        ↓
Canonical Ingredient
```

Planner никогда не должен зависеть непосредственно от названия товара конкретного магазина.

---

# 6. Canonical Ingredient

Это основной нормализованный пищевой ингредиент.

Примеры:

```text
CHICKEN_BREAST
CARROT
BUCKWHEAT
EGG
MILK_2_5
COTTAGE_CHEESE_5
POTATO
SALMON
APPLE
```

Сущность:

`CanonicalIngredient`

Поля:

- id;
- canonical_code;
- canonical_name;
- category_id;
- default_unit;
- density;
- edible_fraction;
- nutrition_profile;
- allergens;
- synonyms;
- storage_profile;
- active;
- created_at;
- updated_at.

---

# 7. Зачем необходим Canonical Ingredient

Например, в магазинах могут одновременно существовать товары:

- «Филе грудки цыплёнка охлаждённое»;
- «Филе куриное без кожи»;
- «Грудка цыплёнка»;
- «Филе грудки Петелинка»;
- «Филе куриной грудки 750 г».

Для Meal Planner всё это должно означать:

```text
CHICKEN_BREAST
```

Planner выбирает ингредиент.

Shopping Engine позднее выбирает конкретный SKU.

Это принципиальное разделение.

---

# 8. Источники первоначального каталога ингредиентов

Каталог не создаётся вручную через UI по одному ингредиенту.

Предусматривается bulk bootstrap.

Источниками могут быть:

- структурированные пищевые справочники;
- официальные или лицензированные базы пищевой ценности;
- подготовленные CSV/XLSX;
- существующие внутренние справочники;
- импорт из существующих проектов;
- автоматически обработанные данные каталогов ритейлеров.

---

# 9. Initial Ingredient Bootstrap

Первичная загрузка выполняется отдельным ingestion job.

Пример:

```text
ingredient_source.csv
        ↓
Parser
        ↓
Normalizer
        ↓
Deduplicator
        ↓
Nutrition Validator
        ↓
CanonicalIngredient
```

Результат первой версии:

**250–350 canonical ingredients.**

Для technical vertical slice допускается:

**80–120.**

---

# 10. Автоматическая нормализация названий

Все входящие названия проходят normalizer.

Например:

```text
"Морковь мытая, 1 кг"
"Морковь свежая"
"Морковь весовая"
"Морковь 500г"

        ↓

CARROT
```

Normalizer должен обрабатывать:

- регистр;
- лишние пробелы;
- тип упаковки;
- массу;
- бренд;
- маркетинговые слова;
- сокращения;
- склонения;
- распространённые синонимы.

---

# 11. Словарь синонимов

Для canonical ingredients необходимо хранить:

`IngredientAlias`

Пример:

```text
CHICKEN_BREAST

aliases:
- куриная грудка
- грудка куриная
- филе грудки
- филе курицы
- грудка цыплёнка
```

Словарь должен постепенно расширяться автоматически.

---

# 12. Автоматическое сопоставление

Pipeline:

```text
Retail Product Name
        ↓
String Normalization
        ↓
Alias Matching
        ↓
Token Matching
        ↓
Category Matching
        ↓
Fuzzy Matching
        ↓
Optional Embedding / AI Matching
        ↓
Confidence Score
```

Результат:

```text
RetailSKU
ingredient_id = CHICKEN_BREAST
confidence = 0.97
```

---

# 13. Confidence Score

Каждое автоматическое соответствие получает показатель уверенности.

Например:

### ≥ 0.95

автоматически принять.

### 0.80–0.95

автоматически использовать, но оставить возможность выборочного контроля.

### < 0.80

отправить в review queue.

Пороговые значения должны быть конфигурируемыми.

---

# 14. Human-in-the-loop

Человек участвует только в сложных случаях.

Пример review queue:

```text
Товар:
"Филе нежное деревенское 750 г"

Предполагаемое соответствие:

1. Chicken breast — 73%
2. Chicken thigh — 19%
3. Turkey breast — 8%
```

Оператор одним нажатием выбирает правильный вариант.

После этого решение сохраняется и используется для будущих аналогичных товаров.

---

# 15. Главный показатель эффективности ingestion

Необходимо измерять:

`Auto Resolution Rate`

То есть долю объектов, обработанных без участия человека.

Целевое значение:

### ранний MVP

>80%

### beta

>90%

### зрелая система

>95%

Человек должен заниматься исключениями, а не вводом каталога.

`RetailSKU`

Поля:

- id;

- retailer_id;
- external_id;
- ingredient_id;
- source_name;
- normalized_name;
- brand;

- package_unit;

- nutrition_label;

- mapping_confidence;

- first_seen_at;

---

# 17. Retail Connectors

Для каждого магазина создаётся отдельный connector.

Пример:

```text
RetailConnector

search()
fetch_categories()
fetch_products()
fetch_product()
fetch_price()
fetch_availability()
normalize()
```

Пример реализаций:

```text
LentaConnector
PyaterochkaConnector
MagnitConnector
```

При изменении одного сайта не должен ломаться весь ingestion pipeline.

---

# 18. Приоритет источников ритейлеров

Используется следующий порядок:

1. официальный API, если доступен;
2. партнёрский API;
3. публичный структурированный каталог;
4. публичные web endpoints;
5. HTML parsing;
6. ручной импорт как fallback.

Не предусматривается обход технических защит сайтов.

---

# 19. Retail Discovery

Система не обязана загружать весь ассортимент магазина.

Она должна сначала понимать:

> какие продукты FamilyFoodOS вообще умеет использовать.

Например, имеется:

```text
312 active CanonicalIngredients
```

Retail Discovery выполняет поиск SKU только для этих категорий.

---

# 20. Whitelist Approach

В MVP поддерживается whitelist.

Например:

```text
CHICKEN_BREAST
CHICKEN_THIGH
EGG
MILK
KEFIR
COTTAGE_CHEESE
POTATO
CARROT
...
```

Это позволяет не индексировать:

- бытовую химию;
- косметику;
- алкоголь;
- игрушки;
- товары для дома;
- тысячи нерелевантных продуктов.

---

# 21. Retail Search Pipeline

Для каждого CanonicalIngredient:

```text
CanonicalIngredient
        ↓
Search Queries
        ↓
Retail Connector
        ↓
Candidate SKU
        ↓
Normalizer
        ↓
Matcher
        ↓
Validation
        ↓
RetailSKU
```

Например:

```text
CHICKEN_BREAST

queries:
"куриная грудка"
"филе грудки"
"филе куриное"
```

---

# 22. Первичное заполнение одного магазина

При первом подключении retailer выполняется batch import.

Пример:

```text
300 CanonicalIngredients
        ↓
поиск
        ↓
4 000 candidate SKU
        ↓
дедупликация
        ↓
1 200 relevant SKU
        ↓
automatic mapping
        ↓
review queue
```

При этом оператор не создаёт 1 200 товаров вручную.

---

# 23. Инкрементальное обновление

После initial import система выполняет только изменения.

Необходимо определять:

- новые товары;
- исчезнувшие товары;
- изменение упаковки;
- изменение цены;
- изменение наличия;
- изменение названия;
- изменение пищевой ценности.

---

# 24. Source Snapshot

Исходный ответ источника желательно сохранять.

Сущность:

`RawSourceRecord`

Это позволяет:

- повторно обработать данные;
- отладить parser;
- изменить normalizer;
- восстановить mapping.

---

# 25. Цена

Цена хранится отдельно от SKU.

Сущность:

`PriceSnapshot`

```text
sku_id
store_id
regular_price
current_price
loyalty_price
currency
availability
captured_at
```

Исторические значения не перезаписываются.

---

# 26. Частота обновления цен

Частота должна настраиваться для каждого connector.

Для MVP ориентир:

- 1–4 обновления в сутки;
- либо обновление перед построением пользовательской корзины;
- либо комбинация этих способов.

Нет необходимости непрерывно опрашивать магазины.

---

# 27. Stale Data

Каждой цене назначается статус свежести.

Например:

```text
FRESH      < 24h
AGING      24–72h
STALE      > 72h
```

Если свежая цена отсутствует, сервис продолжает работать.

Fallback:

```text
latest price
        ↓
average price
        ↓
canonical average
```

---

# 28. Географическая доступность

При наличии соответствующих данных Retail SKU связывается с:

`RetailStore`

или:

`RetailRegion`.

В MVP предпочтительно не использовать точную геолокацию пользователя.

Достаточно:

- города;
- выбранной сети;
- выбранного магазина, если это необходимо.

---

# 29. Пользователь выбирает магазин, а не товары

Onboarding:

> Где вы обычно покупаете продукты?

Варианты:

- Пятёрочка;
- Магнит;
- Лента;
- другие подключённые сети;
- «неважно».

После выбора каталог автоматически ограничивается релевантными SKU.

Пользователь не должен сам искать и создавать товары магазина.

---

# 30. Подбор конкретного товара

Recipe требует:

```text
600 g CHICKEN_BREAST
```

Shopping Engine получает:

```text
Retail candidates:
SKU A — 750 g — 399 ₽
SKU B — 900 g — 449 ₽
SKU C — 500 g — 319 ₽
```

Система сама предлагает оптимальный SKU.

Пользователь может при желании заменить его.

---

# 31. Default product selection

При выборе SKU учитываются:

- наличие;
- цена;
- цена на единицу;
- размер упаковки;
- ожидаемый остаток;
- предпочтительный бренд;
- история покупок.

Изначально:

```text
cheapest suitable SKU
```

либо:

```text
best package fit
```

---

# 32. Product Preference Memory

Если пользователь постоянно выбирает:

> Простоквашино

вместо другого творога,

система может повысить рейтинг данного бренда.

Это не требует AI.

Сущность:

`HouseholdProductPreference`.

---

# 33. Рецепты также не вводятся вручную по одному

Для рецептов должен существовать отдельный bulk ingestion pipeline.

```text
Recipe Source
        ↓
Recipe Parser
        ↓
Structured Recipe Candidate
        ↓
Ingredient Resolver
        ↓
Nutrition Calculation
        ↓
Validation
        ↓
RecipeVersion
```

---

# 34. Источники рецептов

Предпочтительные варианты:

- собственная база;
- лицензированные рецепты;
- подготовленные XLSX/CSV;
- структурированные JSON;
- рецепты специалистов проекта;
- материалы, права на использование которых позволяют включение в продукт.

Внешний текстовый контент не должен автоматически копироваться в production-каталог без проверки прав на использование.

---

# 35. AI-assisted Recipe Import

AI может использоваться как инструмент импорта.

Например оператор загружает:

- DOCX;
- PDF;
- XLSX;
- текст;
- набор внутренних рецептов.

AI преобразует:

> «Возьмите полкило куриной грудки, две луковицы...»

в:

```text
ingredient_id: CHICKEN_BREAST
quantity: 500
unit: g
```

Однако итог проходит детерминированную валидацию.

---

# 36. Recipe Candidate

Импортированный рецепт сначала создаётся как:

`RecipeCandidate`

а не как активный production-рецепт.

Он проходит:

1. syntax validation;
2. ingredient resolution;
3. unit conversion;
4. nutrition calculation;
5. serving validation;
6. duplication check;
7. publish check.

---

# 37. Ingredient Resolution в рецепте

Например источник содержит:

> «2 средние моркови».

Parser преобразует:

```text
ingredient = CARROT
unit = piece
quantity = 2
```

Unit Conversion переводит это в базовую массу:

```text
≈ 160 g
```

Для подобных конверсий хранится:

`IngredientUnitProfile`.

---

# 38. Нормализация единиц

Система должна понимать:

- г;
- кг;
- мл;
- л;
- штука;
- чайная ложка;
- столовая ложка;
- стакан;
- упаковка.

Внутреннее хранение желательно стандартизировать:

```text
mass → grams
volume → milliliters
```

---

# 39. Nutrition Calculation рецепта

Пищевая ценность рецепта не должна слепо копироваться из исходного текста.

Рассчитывается:

```text
RecipeIngredient
        ×
CanonicalIngredient nutrition
        ↓
RecipeNutrition
```

Это обеспечивает единую методологию.

---

# 40. Проверка аномалий

Автоматическая система должна находить ошибки.

Примеры:

- 5 кг соли;
- 20 литров молока на 4 порции;
- 12 000 ккал на порцию;
- неизвестный ingredient;
- отсутствующее количество;
- нулевой вес блюда;
- несовместимые units.

Такие рецепты направляются в review queue.

---

# 41. Duplicate Recipe Detection

При импорте необходимо проверять похожие рецепты.

Например:

```text
Куриные тефтели
Тефтели из куриного фарша
Домашние куриные тефтели
```

Могут быть:

- одним рецептом;
- версиями;
- различными вариантами.

Система должна показывать оператору потенциальные дубликаты.

---

# 42. Рецепт и меню — разные сущности

Меню не должно храниться как заранее написанный текст.

Меню является результатом Planner.

```text
Recipe Catalogue
        +
Household
        +
Constraints
        +
Pantry
        +
Budget
        ↓
Meal Planner
        ↓
Weekly Menu
```

Поэтому вручную «загружать меню» в большинстве случаев вообще не требуется.

---

# 43. Template Menu

При необходимости допускаются:

`MealPlanTemplate`

Например:

- бюджетная неделя;
- быстрая неделя;
- детская неделя;
- freezer week.

Но template содержит не фиксированный текст, а правила и предпочтительный набор рецептов.

Planner адаптирует его под конкретную семью.

---

# 44. Импорт внешнего меню

Future feature.

Если пользователь или специалист загружает готовое меню:

- PDF;
- таблицу;
- текст;

система может выполнить:

```text
Menu Import
        ↓
Meal Extraction
        ↓
Recipe Matching
        ↓
Ingredient Resolution
        ↓
Nutrition Validation
        ↓
MealPlan
```

Пользователю не приходится переносить каждый день вручную.

---

# 45. Pantry — минимизация ручного ввода

На MVP полностью автоматизировать содержимое холодильника невозможно.

Однако ручной ввод необходимо максимально сократить.

Основные механики:

### 1. Из shopping list

Пользователь отметил:

> «Куплено»

Товары автоматически добавляются в Pantry.

### 2. Из предыдущей недели

Неиспользованный остаток автоматически переносится.

### 3. Быстрый поиск

Пользователь вводит:

> рис

и выбирает готовый вариант из каталога.

### 4. Frequently Used

- canonical fingerprint.

- назначить ingredient;
- подтвердить;

Alias сохраняется.

# 63. AI в ingestion pipeline

AI является необязательным ускорителем.

Возможные задачи:

- extraction из неструктурированного текста;
- categorization;
- ingredient mapping;
- recipe parsing;
- synonym generation;
- duplicate detection.

Но AI не должен напрямую публиковать критические данные без validation layer.

# 64. Работа ingestion без AI

При отключённом AI остаются:

- exact matching;
- alias matching;
- fuzzy matching;
- category rules;
- regex;
- unit parser;
- deterministic validators;
- review queue.

Таким образом каталог можно поддерживать полностью без внешней нейросети.

# 83. Основное отличие от «Мастерской»

В «Мастерской» ингредиент чаще является управляемой пользователем производственной сущностью.

В FamilyFoodOS каталог является:

> **центрально управляемой платформенной сущностью.**

Обычный пользователь не владеет каталогом ингредиентов.

Он только использует его.

Это существенно упрощает UI.

# 89. Acceptance Criteria — данные

Система считается готовой по ingestion части MVP, если:

1. каталог ингредиентов загружается batch-операцией;
2. оператор не создаёт ингредиенты по одному;
3. рецепты могут импортироваться массово;
4. ингредиенты рецептов автоматически сопоставляются с canonical catalog;
5. nutrition рассчитывается автоматически;
6. неизвестные объекты попадают в review queue;
7. пользовательский UI не содержит формы создания системного продукта;
8. Shopping List строится автоматически;
9. Pantry использует существующий catalog;
10. повторный импорт не создаёт дубликаты.

---

# 90. Acceptance Criteria — retailer integration

При подключении магазина:

1. connector получает товары автоматически;
2. товары нормализуются;
3. упаковка извлекается автоматически;
4. цена извлекается автоматически;
5. товар связывается с canonical ingredient;
6. high-confidence mapping принимается автоматически;
7. сомнительный mapping попадает в review;
8. новая цена создаёт PriceSnapshot;
9. недоступность parser не ломает Planner;
10. пользователю не требуется вручную создавать SKU.

---

# 91. Acceptance Criteria — UX

Обычный пользователь никогда не должен столкнуться с обязательным полем:

- «создать ингредиент»;
- «калорийность продукта»;
- «белки»;
- «жиры»;
- «углеводы»;
- «категория продукта»;
- «код магазина»;
- «SKU ID».

Эти данные принадлежат платформенному слою.

> **system of defaults, not system of forms.**

То есть система поставляет пользователю готовый разумный результат.

Пользователь изменяет только то, с чем не согласен.

# 94. Главный продуктовый результат

После реализации данного подхода FamilyFoodOS должен работать следующим образом:

> пользователь рассказывает системе только то, что она не может узнать сама.

Всё остальное:

- ингредиенты;
- пищевые данные;
- рецепты;
- цены;
- товары;
- упаковки;
- сопоставления;
- меню;
- закупка;
- расчёты;

подготавливает сама платформа.

Таким образом сложность backend и ingestion pipeline несколько увеличивается, но пользовательский интерфейс становится существенно проще.

Это сознательный архитектурный компромисс:

> **сложность должна находиться внутри системы, а не перекладываться на пользователя.**
