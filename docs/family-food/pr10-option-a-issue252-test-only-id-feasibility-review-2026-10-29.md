## FACT — what the existing API actually supports

1. `backend/app/services/food_recipes.py::FoodRecipeCatalogueService.__init__(..., *, id_factory=uuid4)` accepts an injectable **zero-argument UUID producer**. Its `_new_recipe` and `_new_detail` consume the same producer for **Recipe, RecipeVersion, RecipeIngredient and RecipeStep** IDs; this is **not** an ID resolver keyed by canonical recipe/source/version. Arbitrarily replaying only 51 historical active RecipeVersion UUIDs through the producer would assign them to the **wrong object types**.
2. `backend/app/persistence/sqlalchemy_core/food_recipe_composition.py::create_food_recipe_catalogue_service(engine)` exposes **only `engine`**, so the production seed entrypoints call the normal UUID generator. This is a real missing *end-to-end explicit test seam*, not proof the domain Planner is wrong. A generic global UUID monkeypatch, replacing the production composer globally, direct SQL ID mutation or bypassing rights/FKs is **not permitted**.
3. **Verified seed propagation path:** `seed_dc4_a3_russian_step_corrections` → `seed_r3d_final_dc3_batch` → `seed_r3c_school2022_main_batch` → R3A and R3B branches → `seed_r2f_cheese_sandwich` → `seed_r2e_cottage_casserole` → `seed_r2c_breakfast_grain_diversity` → `seed_r2b_fish_main_diversity` → `seed_r2_breakfast_capacity` → `seed_r1h_school2022_main` → `seed_r1f_prepared_output` (plus ingredient/nutrition prerequisites). Multiple nested functions call `create_food_recipe_catalogue_service(engine)` independently; **a single test-only argument at the top does not flow through**. Many modules would need explicit optional injection propagation, or another reviewed narrowly bounded mechanism. Don't assume a change in one constructor stabilizes all 51.
4. `HouseholdService` **also accepts** an `id_factory`, but its normal composition does not propagate it. Historical `MemberPlannerConstraints` and accepted MealPattern selections involve UUIDs, and the Planner sorts members by `member_id.hex` and candidates by `recipe_version_id.hex`. Stable RecipeVersion identity alone is not yet shown sufficient for **historical schedule or per-member Decimal factor parity**. Keep actual Household/Member/Serving FK validation.
5. The archived historical [receipt](evidence/pr196-original-synthetic-fixture-receipt.json) pins all **51 active RecipeVersion UUIDs**, their canonical source IDs/version/document SHA, ordered Step instruction digests, **three historical member UUIDs** and original 21×42 positive Decimal factors. It **does not pin** every superseded historical RecipeVersion/RecipeStep ID created during incremental seed, a complete serialized `PlannerRequest`, original candidate *calculated kcal* and scoring trace input, or an explicitly versioned complete seed call-order manifest.

**Source comparison (the two real test runs vs original):** **51/51** canonical source identity + ordered UUID-free Step content equal; **0/51** active RecipeVersion UUID equal to the historical receipt, **0/3** member UUID equal. Both fresh runs persisted 3/21/42 genuine structures but gave different weeks: run 1 0/21 and run 2 1/21 historical selected recipe/date slots. **Do not infer** UUID is the sole cause from this correlation.

## ASSUMPTION / recommended bounded future design (not implemented)

An **explicit, opt-in fixture-only ID mapping** could be feasible if an independently reviewed dependency graph propagates a typed identity factory through *every* seed creator and Household composition path, while the ordinary production path continues to use `uuid4` without any hidden global state. Required semantics:

- Map key must contain **entity type, canonical recipe code, source name, source recipe ID/version/document hash and ordinal/version lineage** where applicable; never use a bare ordered list of 51 UUIDs. The mapping must validate originals against the archived raw historical receipt and reject duplicate UUIDs across Recipe/Version/Ingredient/Step/Member/Housing scopes.
- **Historical source rights/verification, ingredient form and immutable Step content are checked from current trusted service storage**, not accepted because a stored fixture claims them.
- Do not make the normal catalogue seed or production Planner depend on historical UUIDs. No `uuid4` monkeypatch, dynamic global context override, direct SQLite data rewrite, candidate filtering/ranking tweaks, fixed MealEvent override or fabricated snapshot-only Planner PASS.
- Audit all historical input fields **before** treating exact selected slots as causal evidence of an ID fix. Two separate temp SQLite **full** seeds, unchanged `PlannerService.generate_authoritative`, persisted/current-plan readback and 42 exact Decimal participant servings must yield the accepted ID-free SHA256 `731ef32e7137740ed5b46a6044a85d8b2f818a847fdc039842460d442df5aeb6`.
- If the *minimal* change actually requires a new production service/composition contract or schema/seed authority, submit a **separate reviewed docs-only amendment/owner decision** first under the accepted [Option A contract](pr10-core-option-a-stable-fixture-implementation-contract-2026-10-27.md). Do not widen the current evidence PR into a 12+-stage seed rewrite without approval.
