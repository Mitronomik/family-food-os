## 1. FACT / ASSUMPTION / PROPOSED DECISION / OPEN

**FACT:**
- `HouseholdMealEvent` is currently a `MealSourceKind.COOK_RECIPE` event with one `recipe_version_id`, or a non-recipe source with no `recipe_version_id`. It does **not** have an authoritative multi-recipe mode. `Serving(event_id, member_id, portion_servings)` is unique per event/member and means a scale of the event's one RecipeVersion.
- `MealPlan` is immutable and versioned by `(household_id, week_start, revision_number)`, with `supersedes_plan_id`. `SqlAlchemyMealPlanRepository.add_detail()` inserts plan, member selection/reference pins, events, Servings within one UoW; `get_detail(household_id, plan_id)`, `get_current(household_id, week_start)`, `list_history()` are household-scoped.
- SQLite migration registry currently ends at `0043_shopping_engine`; `0033` remains reserved and is **not** inserted into the already accepted prefix. The custom SQLite migration runner is the sole authority. `meal_plan_events.source_kind` is CHECK-constrained and `COOK_RECIPE` requires a non-null recipe. Events, Servings and MealPlan revisions have immutable-row triggers.
- Shopping v1a iterates persisted `MealPlanDetail.events` + legacy `Serving`; for `COOK_RECIPE` it multiplies each pinned ingredient by sum of Servings/base. It does **not** read component Servings. A composed event masquerading as ordinary `COOK_RECIPE` would **under-count or double-count** groceries. `EAT_OUT` has no recipe-demand expansion.
- #290's `MealEventCompositionDraft`, `MealComponentDraft`, `MemberComponentServingDraft` and explicitly selected `RequiredCourseCoverage` validate **structure only**; they neither validate full nutrition, recipe suitability, physically feasible portions nor Shopping/Prep authority.
- For the accepted illustrative Tuesday 2026-11-03 lunch, member #1 is the only at-home lunch participant; members #2/#3 have no home lunch and must not acquire phantom events, kcal or groceries.

**ASSUMPTION TO CHALLENGE:** an additive immutable set of component tables, plus a strictly new source kind that old engines cannot interpret as ordinary recipe demand, is the smallest safe persistence evolution. SQLite table rebuilding can preserve all historical `meal_plan_events` dependent FKs and triggers if a fresh/upgrade/failure-injection proof passes.

**PROPOSED DECISION:** use a new `COOK_COMPOSITION` meal-event source kind for **new, complete seven-day, explicitly diagnostic-only DRAFT plan revisions**, with an **immutable full snapshot of the versioned course rule** and exact member-component Servings persisted atomically. Clone every unchanged event/Serving and all accepted pins from the previous week revision; change exactly the chosen meal. Preserve all existing `COOK_RECIPE`/legacy `Serving` semantics without backfill. **Do not activate composite events as accepted consumer plans or Shopping demand in the persistence PR.** A later separately reviewed Shopping/context integration is a distinct authorization, not an implicit permission from storing rows.

**OPEN FOR OWNER/REVIEWER:** exact public API shape for a future consumer multi-course editor, eventual approved role policy and source rights, physical portion eligibility, final transition from diagnostic DRAFT to an authoritative composition with compatible Shopping/Prep/Nutrition. None of these questions may be silently resolved by the first persistence PR.

## 2. Ownership and compatibility options

| Option | Consequence | Disposition |
| --- | --- | --- |
| A. Add components to a legacy `COOK_RECIPE` event, leaving old `Serving` as an anchor | Existing Shopping/Nutrition/Prep silently read **only** the primary recipe; adding component rows after the fact also undermines immutability | **REJECT** |
| B. Represent a multi-course meal as `ASSEMBLY` | Conflates a multi-course meal with a recipe assembly that has independent source/composition authority | **REJECT** |
| C. Separate new `COOK_COMPOSITION` source kind, explicit component rows and member-component Servings, new append-only DRAFT MealPlan revision | Requires a CHECK-preserving migration rebuild, explicit mixed-read handling and fail-closed downstream tests; no silent ingredient demand | **RECOMMENDED (proposed)** |
| D. Store free-form JSON as `source_reference` | No typed source-pin/Decimal identity; weak constraints, poor auditing and migration to Shopping | **REJECT** |

The role rule is an explicit, versioned research/proposal input, **not** a published `MealPatternProgram`. Its `coverage` must be explicit: for the requested home lunch, `FIRST` and `SECOND` are mandatory **PER_PARTICIPANT**, while `DESSERT` has `minimum=0`. `EVENT` is allowed as a separate, explicitly weaker draft rule and must never be treated as per-person completeness. **The full ordered `requirements` (course kind, minimum, maximum) must be durably persisted**, not looked up solely by `code/version` after process restart; §3 specifies the immutable-snapshot option.

### 2.1 Source-kind and legacy contract

- Add `MealSourceKind.COOK_COMPOSITION` to domain, SQL CHECK and adapter/read mapping only in the **future runtime PR**. It means **multiple immutable recipe versions under one eating opportunity**, not an invented RecipeVersion/RecipeAssembly.
- For `COOK_COMPOSITION`, the parent `meal_plan_events.recipe_version_id` MUST be NULL and `source_reference` MUST be NULL. Its source authority comes from all child `recipe_version_id` pins.
- `COOK_RECIPE` and all historical non-recipe kinds remain byte-identical, semantically unchanged and read without synthetic component rows or altered Serving values.
- `COOK_COMPOSITION` has **no legacy `servings`**. Its participant set is the union of exact child component Servings. Do **not** insert fake `Serving.portion_servings=1` attendance rows, which would mislead Nutrition/Shopping.
- The original #289 `MealPlan` remains immutable. The new sample is a separate append-only **complete seven-day revision** with its own plan/event/Serving UUIDs and correct `supersedes_plan_id`; **every untargeted event, its per-member Servings, selection pins and reference-methodology pins are copied into the new immutable snapshot**, not silently omitted. Existing plans are neither rewritten nor assigned sidecar components. The only intentional semantic change is the chosen LUNCH event; see §3.2.

## 3. Proposed additive data model and source pins (future migration 0044, pending availability check)

Migration candidate name: **`0044_meal_plan_components`** — verify it remains unallocated against latest `main` **at runtime start**. Do not change `MIGRATION_MODULES` in this docs PR.

**Parent:** existing `meal_plans` (household/week/revision) and `meal_plan_events` (local day, position, role). New event `source_kind=COOK_COMPOSITION` with null `recipe_version_id`. The new plan revision contains **all seven days and every original meal event** (§3.2), not just a new event; it has newly keyed copies of the prior `meal_plan_member_selections` and exact reference-methodology snapshots, still referencing their unchanged accepted selection/version identities.

**New tables (proposed names and key constraints):**

| Table | Columns and hard keys | Role |
| --- | --- | --- |
| `meal_plan_event_compositions` | `event_id PK/FK → meal_plan_events.id`; `structure_rule_code TEXT NOT NULL`, `structure_rule_version INTEGER >0`, `required_coverage ENUM(EVENT,PER_PARTICIPANT)`; **`rule_snapshot_schema_version INTEGER NOT NULL` (initially 1), `requirements_json TEXT NOT NULL`, `rule_snapshot_sha256 CHAR(64) NOT NULL`**; `admission_status='DIAGNOSTIC_ONLY'`, `created_at` | Complete **immutable ordered course-requirements snapshot**, digest-bound to rule identity and parent event role. No live catalogue lookup or implicit role template/physical PASS |
| `meal_plan_event_components` | `id UUIDv4 PK`; `event_id FK → meal_plan_event_compositions.event_id`; `position INTEGER >0`; `course_kind` from PR290 `MealCourseKind` (not `RecipeVersion.meal_type_code`); `recipe_version_id FK → food_recipe_versions.id`; `created_at`; `UNIQUE(event_id,position)` | Ordered, immutable source-pinned recipe component |
| `meal_plan_component_servings` | `component_id FK → meal_plan_event_components.id`, `member_id FK → household_members.id`, `portion_servings TEXT NOT NULL` (exact positive finite Decimal, 0.000001 precision), `created_at`; `PRIMARY KEY(component_id,member_id)` | One physical allocation per participant and component. Not a legacy event Serving |

**Schema guarantees:** SQLite `FOREIGN KEY`/CHECK/UNIQUE, canonical 32-char UUID encoding, required course-kind enum, positive integer positions, immutable UPDATE/DELETE triggers on all new tables, indexes for event/position and component/member, `ON DELETE RESTRICT`. `requirements_json` must be valid JSON with a bounded array, and `rule_snapshot_sha256` exactly 64 lowercase hex characters (DB CHECK plus independently computed hash/typed reconstruction in domain/UoW; a SQLite `json_valid` or hash-shape CHECK alone does **not** establish rule correctness). In SQLite, a simple CAST-only CHECK is insufficient to prove valid canonical Decimal: application validation and negative SQL tests must reject `NaN`, scientific notation, locale commas, negative/zero, too many fractional digits and excessive magnitude. No float or silent quantization. A direct DB write that is well-formed but would create an incomplete multi-course event must remain **inaccessible outside the tested UoW**; domain + repository transactional validation are mandatory.

**Necessary cross-row invariants (application/domain + UoW):**
1. New parent event belongs to the **new** Household-owned MealPlan revision and is `COOK_COMPOSITION`. Parent and components are inserted in the **same transaction**. Each child recipe must be an exactly pinned, verified/reviewed eligible `RecipeVersion`; no synthetic recipe identity.
2. One composition header per event; 1..N components, contiguous positions, distinct component identity; course kinds comply with the **complete immutable rule snapshot**, not a mutable code/version lookup. Preserve #290's exact cardinality semantics: `minimum/maximum` bound **event-wide** component counts, and for `PER_PARTICIPANT` the minimum is **additionally** required for every actual home member; optional kinds (`minimum=0`) may be absent for individual members. Full ordered `requirements`, schema version, cross-fields and snapshot hash must round-trip across processes (§3.1).
3. Attending members belong to the plan's **pinned Household selections**, have explicit selected at-home opportunities for that local date/role and pass hard ingredient exclusions. No out-of-home placeholder meal. Component Serving positive exact Decimal and member/component unique. No unauthorized household cross-reference.
4. `COOK_RECIPE` retains its historical event-level `Serving` rows and immutable recipe pin. `COOK_COMPOSITION` has **only** member-component Servings, with no legacy Serving. Every stored component must have at least one participant; every attending member must meet the draft role rule's mandatory courses.
5. `admission_status=DIAGNOSTIC_ONLY` and `MealPlan.status=DRAFT` are enforced **before commit**; no public CONFIRMED composition, no partial plan writes. Source-ingredient/canonical FoodIngredient authority, unknown nutrients, member contraindications and physical portion feasibility remain separate reviews; passing structure is not their substitute.
6. A plan revision cannot be mutated by adding/removing child components, course rules or member assignments after its initial transaction. New choices always create **another complete seven-day plan revision**, not an in-place edit or a one-event delta. The new revision must satisfy the semantic preservation matrix (§3.2).
7. Deterministic ordering is `(local_date, event.position, component.position, member UUID)`, preserving Household-local date; no implicit per-day energy redistribution.

### 3.1 P2 decision — persist the *complete immutable* course rule (snapshot option)

**Selected design: per-composition immutable snapshot, not an unresolved external rule registry.** The approved non-persistent `DraftMealStructureRule` has **five** effective fields: `code`, `version`, `meal_role`, `coverage` and an **ordered** `requirements: tuple[CourseCardinality, ...]` where each requirement includes `kind`, integer `minimum` and integer `maximum`. The runtime PR must store *all* of them. A `code + version + coverage` reference alone is insufficient because no accepted immutable course-rule catalogue exists.

- Store `requirements_json` in the composition header as a **canonical UTF-8 JSON array**, in the explicit `requirements` order. Each entry has exactly `{"kind": "FIRST", "minimum": 1, "maximum": 1}` (keys shown for illustration), with strict whitelisted `MealCourseKind`, **integer** min/max (no bool, float, numeric strings), `0 <= minimum <= maximum`, maximum positive and unique kinds; no unknown fields, gaps, duplicates, hidden defaults or silent sorting. JSON serialization must be deterministic, with fixed key ordering, whitespace policy and stable UTF-8 encoding. The order is part of the rule: FIRST then SECOND then optional DESSERT.
- Compute `rule_snapshot_sha256` as SHA-256 over canonical UTF-8 bytes of the **full, typed rule snapshot**: `{schema_version: 1, code, version, meal_role, coverage, requirements}`. Persist `schema_version` in `rule_snapshot_schema_version`; the first accepted format is **1**, and readers must reject unknown future versions instead of defaulting them. The separately stored header `structure_rule_code`, `structure_rule_version`, `required_coverage` and parent `meal_plan_events.role_code` **must equal** the parsed snapshot. Mismatches or hash changes block read/write; never quietly substitute a current rule definition. The digest provides corruption/drift detection, **not** cryptographic authorship or independent review.
- On **every read**, reconstruct `DraftMealStructureRule` and `CourseCardinality` from this immutable snapshot, check the digest and cross-fields, validate all components and `MemberComponentServing` against **the restored rule**, then produce typed `MealPlanDetail` or fail closed. No lookup by code/version alone and no fallback to a newly edited Python rule or future `MealPatternProgram`. Fail closed for unrecognized schema versions or malformed snapshot bytes.
- A rule change to FIRST/SECOND/DESSERT counts, coverage, order or constraints requires a **new rule version AND a new complete MealPlan revision**. If the same `(structure_rule_code, structure_rule_version)` is submitted with a different snapshot hash than a previously stored definition, reject it as an identity conflict rather than reinterpreting old rows. Check this atomically in the single-writer UoW/DB write transaction; regression tests must include concurrent conflicting writers. The embedded snapshot remains authoritative for historical replay even if a later curated rule catalogue changes.
- **Case snapshot (test fixture, not production role approval):** `DEV_LUNCH_FIRST_SECOND_OPTIONAL_DESSERT@1`, `meal_role=LUNCH`, `coverage=PER_PARTICIPANT`, ordered `requirements=[(FIRST,1,1), (SECOND,1,1), (DESSERT,0,1)]`. This preserves the P2 fix from #290: every participating member gets FIRST and SECOND, while DESSERT may be skipped independently. It does not assert that the proposed dessert recipe is suitable or that any physical portion is approved.

### 3.2 P2 decision — new revision is a *complete seven-day MealPlan snapshot*

**Selected model: full new MealPlan revision; NOT an isolated one-lunch plan or delta.** A `MealPlanDetail` is a complete immutable week and must never be derived by overlaying a single changed event at read time. Any diagnostic composed lunch in a new revision starts from a **specific pinned complete previous revision**. The one-lunch example in #289/#290 changes **exactly one chosen at-home LUNCH** and preserves the rest.

1. **New plan identity:** allocate a new `MealPlan.id` (UUIDv4), same `household_id` and `week_start`, `revision_number = previous.revision_number + 1`, `supersedes_plan_id = exact previous plan.id`, `status=DRAFT`, and an explicitly pinned compatible planning/config/structure version. No edits to previous plan IDs or history.
2. **Copy all seven-day events:** the new revision contains **one event for every original `(local_date, position)`** across the whole week, with a **new event UUIDv4 and `plan_id=new_plan.id`**. For every **untargeted** event copy exactly the semantic fields `local_date`, `position`, `role`, `source_kind`, nullable `recipe_version_id`, and `source_reference`; preserve source integrity and chronological/contiguous ordering. A fresh `created_at` is audit metadata, not a basis for changing or omitting meals. Never reuse an old event UUID across revisions or create an outside-home filler event.
3. **Copy all original untargeted Servings:** for every unchanged event and participant, create a **new `Serving.id` UUIDv4** with `event_id` pointing to that event's **new** UUID, unchanged `member_id` and **exact unchanged `Decimal portion_servings`** (no float, conversion, rounding or normalization drift). This applies to all source kinds according to the prior complete plan, including non-recipe events; no orphan or duplicate assignments. All old event/Serving rows remain immutable.
**Additional invariant — if the previous revision already has other composed events:** for **every untargeted `COOK_COMPOSITION` event**, also clone its exact `requirements_json`, rule schema/version/coverage/hash, every component with a new component UUID and `event_id` remapped to the new event, and each component Serving with its `component_id` remapped, preserving recipe-version IDs, participant IDs, course positions and exact Decimal factors. The snapshot hashes remain unchanged. Never drop an earlier composed event to accommodate the newly edited lunch; if this general mixed-revision case is not yet implemented, **reject the new revision** rather than writing an incomplete week. This must be exercised when a later composed revision is available.

4. **Copy all plan pins:** create new `MealPlanMemberSelection.plan_id` values referencing the new plan but **retain the exact accepted `member_id → selection_id` mapping**. Clone all existing `MealPlanMemberReferenceMethodologyPin` rows to the new plan ID with the exact reference-methodology-selection ID, anthropometrics/goal/activity, `member_updated_at` and other snapshot values. Any accepted selection opportunity/energy-share verification uses these same immutable accepted versions; do **not** silently re-pin to a changed member state or take a fresh nutrition measurement. Missing or stale pins block write.
5. **Replace only target LUNCH:** the target's new event UUID occupies the **same day/position/role** but is `COOK_COMPOSITION`, with null parent `recipe_version_id/source_reference`. Its old event-level `Serving` rows **are not copied**. Instead insert its immutable rule snapshot, FIRST/SECOND/optional DESSERT component rows, and independent `MemberComponentServing` rows; the union of component participants must equal the original target event's exact member set, and any `PER_PARTICIPANT` required courses must cover every such member. No other event may become composed implicitly.
6. **Complete-week validator and transaction:** validate the **whole reconstructed revision**, not only the changed lunch. Adapt `validate_complete_plan` (or a versioned compatibility wrapper) so that an event's participating members are obtained from **legacy `Serving`** for old kinds and **component Servings** for `COOK_COMPOSITION`, **never** from a fabricated legacy Serving. Match all required selected at-home opportunities for every member on all seven days, reject extra/omitted slots, unchanged event/participant differences, duplicate positions, broken FK mapping, wrong household, or incomplete pins. Run validation and writes within a single UoW transaction; any error rolls back the **entire** new revision and all child data.

**Semantic preservation proof:** compare old vs new plans after replacing UUIDs by the deterministic `(local_date, position)` mapping. Require exactly one intentionally changed target event; for **all other events**, role/source/recipe/source reference, exact member set and portion factors, order and accepted Household/reference pins must be **equal**. For the actual 21-event synthetic week, the new snapshot still has **21 MealEvents**, with the **20 unchanged events** and all of their historical-equivalent Servings preserved; the former single legacy Serving of the targeted LUNCH is replaced by the three component Servings of that member (do not claim a legacy Serving total of 42 in the new revision). Historical revisions retain their original exact 21/42 readback and semantic SHA. The source `week_start` and all selected non-target home-meal obligations remain intact. If anything is missing, the result is **NO_GO**, never a one-meal `get_current` snapshot.

### 3.3 Rollout hold: current-plan and Shopping safety

**Critical accepted behavior:** current `SqlAlchemyMealPlanRepository.get_current(household_id, week_start)` returns the **highest revision, regardless of DRAFT/CONFIRMED status**. Thus creating a diagnostic composition revision for an already active household/week would immediately change what existing readers consider `current`, and could make prior Shopping snapshots stale *before* any component-aware Shopping engine exists. This is **not permitted as a routine user write** in the first runtime PR.

Until a separately reviewed activation plan and component-aware Shopping/consumer readers exist, `add_diagnostic_composition_revision` must be **developer/test-only**, without a public API, normal Planner invocation, or production-household enrollment; use a dedicated synthetic Household/isolated test database for the demonstration. Do not silently change `get_current` selection semantics to hide DRAFTs: that would be a different behavior contract and would break existing callers. Tests must prove the old operational plan and Shopping state are unaffected by normal application paths. Any subsequent proposal to enable diagnostic revisions in an active Household/week must revisit this gate and explicitly address current-plan selection, derived-state staleness, and the reader capability matrix. A local prototype is not authorization to deploy or expose the writer.

### 3.4 Domain / repository / application shape

- Extend `MealPlanDetail` **additively** with typed read-only composition tuples defaulting to `()` for historical callers. Preserve the old tuple-of-legacy-Serving API for `COOK_RECIPE` events; introduce explicit `composed_event_details` / `component_servings` **including the reconstructed full immutable rule snapshot** for the new kind, not fictitious legacy Servings. Whole-week validation must include unchanged cloned events and pins (§3.2). Existing `MealEventCompositionDraft` and validator from #290 can be adapted for the new event source with explicit input references; their current source-anchoring assumption (`COOK_RECIPE` original) cannot be reused blindly.
- Add an **explicitly named** repository/UoW operation (e.g. `add_diagnostic_composition_revision(...)`) rather than making generic `add_detail()` accept an incomplete composition. The service owns member/selection, source-verified recipe/ingredient and admission checks. The repository owns transactional writes and conflict translation; no SQL in domain/services.
- Reading `get_detail(household_id, plan_id)` and `get_current(household_id, week_start)` returns the **complete seven-day revision**, explicit typed components and per-component Servings, and the original **full ordered rule snapshot** when present; the repository must restore and revalidate the stored rule from its JSON/digest after a restart, never look it up via mutable code/version. Existing callers still get legacy events/Servings unchanged for legacy revisions. Missing unchanged weekly events, snapshot drift or malformed partial data are **fail-closed**, never treated as a valid one-recipe meal.
- `MealPlanNutrition` calculation, derived weekly UI/PDF, Planner historical traces, Shopping and Prep must **fail closed or explicitly report unsupported composition** until their separate integration is accepted. In particular, Shopping v1a must **never** count a primary recipe as a substitute, double-count components, or declare `COMPLETE` on a `COOK_COMPOSITION` event. New source kind must enter no implicit `COOK_RECIPE` calculation branch.
- Canonical `source_fingerprint` for future Shopping will pin **each** component position, RecipeVersion immutable source id/hash/version, exact member Serving, source plan revision and Pantry snapshot, with deterministic aggregation by canonical FoodIngredient+unit. That algorithm, idempotency and staleness are **owned by the future Shopping PR**, not implemented or authorized here.

## 4. Migration safety, replay, rollback and failure semantics

**Preferred migration shape:** `0044` adds three tables. To extend the existing `meal_plan_events.source_kind` CHECK **without dropping integrity**, use the already supported `foreign_key_rebuild` migration mode where necessary. Recreate the parent table with the original constraints, indexes, immutable triggers, FK relationships, original rows and only the added `COOK_COMPOSITION` enum/null-recipe semantics. The runner's rebuild mode disables FKs on a dedicated connection inside a managed transaction, owns the migration marker and executes `PRAGMA foreign_key_check` before commit. Never use Alembic/ORM/`create_all` or `executescript` in the foreign-key rebuild transaction. Do **not** alter accepted `0032`, `0037`, `0043` or earlier migration bytes.

**Risk:** `meal_plan_events` is referenced by historical `servings`, `shopping_` metadata/allocations and potentially other dependent tables. Before choosing the exact SQL rebuild, inventory **every** referencing FK, trigger and index on the runtime HEAD, and prove the rebuilt table is semantically identical for every preexisting source kind. If this cannot be done safely with the existing runner, **stop and amend this contract**, not a best-effort table rename that breaks historical FKs. No orphaned child rows or dropped immutability trigger.

**Fresh:** empty SQLite applies migrations in exact existing order ending 0043, then 0044; `expected_migration_ids`, metadata parity, `PRAGMA foreign_key_check`, snapshot equality; initial schema has no synthetic component rows.

**Replay/upgrade:** a DB already at 0043 with legacy multi-week MealPlans, `member_meal_pattern_selections`, reference pins, old Servings and Shopping snapshots upgrades to 0044 while preserving row counts/identities/quantities and the **exact historical plan fingerprint**. Every newly written composed revision must itself be a full seven-day snapshot of the previous plan, including unchanged slots and pins (§3.2); this is not a migration-time backfill of historical plans. Running `apply_migrations` again is a no-op. No backfill, content rewrite, source-kind recoding, or presentation changes on historical plans. Previously known weekly `get_current` and `list_history` remain well-defined.

**Conflict/failure injection:** invalid UUID or orphan component/Serving; duplicate position or member/component; wrong Household or plan; truncated course set; malformed/missing ordered rule requirements, changed rule body under the same code+version, corrupted canonical JSON/SHA, unrecognized snapshot schema or cross-field mismatch; missing unchanged weekly event, lost legacy Serving or plan pin, incorrect new event/Serving ID remapping; negative/overprecision Decimal; forbidden course/missing member; stale selection/reference or source Version; simultaneous revision creation; new migration interrupted after the first DDL/row copy, after indexes/triggers, or before marker; failure after writing parent/event but before final component Serving; failed user validation; readback corruption. Every path must rollback *entire* new revision and its children with no partially visible current plan/Shopping state and no partial migration marker. Verify failure error is stable and non-leaky.

**Rollback:** migration downgrade is **not** an in-place deletion of new tables or old revisions. Restore a verified pre-upgrade backup as the recovery path if a migration is not safely completed; test backup/export and restore against existing migration ledger. For an application-only rollback after 0044, keep schema additive and old readers operational; new composed DRAFT revisions remain stored/blocked, never silently converted to legacy `COOK_RECIPE` events. If pre-upgrade binary cannot handle a new `COOK_COMPOSITION` current revision, use an explicit compatibility/rollout hold before enabling writers.
