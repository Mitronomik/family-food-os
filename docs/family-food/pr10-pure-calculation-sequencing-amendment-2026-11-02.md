## 3. Proposed Stage A — internal pure diagnostic calculator (future PR10-A1)

A1 is a pure backend-domain calculation function over validated **immutable, Household-scoped, version-pinned input objects** supplied by its caller. It has **no filesystem, SQL/ORM, network, LLM, clock, UUID generation, side effects, API or persisted PrepPlan**. Domain code does not fetch the authoritative snapshot: adapters/services do so later at the accepted boundary. All critical quantities use `Decimal`, never `float` or prose parsing.

**It MAY:**
1. Validate a pinned MealPlan revision, existing RecipeVersionDetails, event/member Serving joins, ingredient identity/unit/form and source rights/status; fail closed for corrupt/missing required facts, cross-Household access or non-finite/nonpositive quantities.
2. For each valid `COOK_RECIPE` event compute `target_servings = sum(participating Serving.portion_servings)`, and exact scaled source `RecipeIngredient` quantities with the accepted base-serving and unit semantics. Do not mix raw/cooked forms or independently synthesize nutrition or output-yield values.
3. Produce deterministic per-event **ingredient requirements**, a **non-actionable candidate metadata** view referencing existing Step identities/provenance only (not instructional user copy), and typed structured **unresolved obligations** for absent/unreviewed/inapplicable permissions and missing process/storage authority. Other legitimate meal-source kinds are represented explicitly, including outside-home with no implied home prep.
4. Return a reproducible **diagnostic** trace/content fingerprint and source/version/policy/revision pins; ensure changed input or revoked/absent status makes any later executable output unavailable. At A1, approval is **not an input inferred from provenance**, and positive executable output is always empty.
5. Handle an entirely unreviewed or all-UNKNOWN week as **diagnostic incomplete**, not as success of an executable plan. Preserve unsupported facts as UNKNOWN, not zero or false certainty.

**It MUST NOT:**
- Create a domain/API/persisted executable `PrepTask`, a consumer-facing preparation instruction, a trusted eligibility grant, `PrepPlan.COMPLETE` or Gate2 PASS from unreviewed Step text, no-digit regex, test-only UUID, reviewer placeholder or a future `APPROVED_IMMEDIATE` count.
- Assume cooking, washing water, yield, capacity, temperatures, intervals, cooling, storing, freezing, thawing or reheating procedure. Never promote `batch_friendly`, `freezable` or null time to safe procedure/zero minutes.
- Group or deduplicate work across MealEvents absent accepted versioned shared-process authority; claim saved shopping time, fewer sessions, money, reduced waste or `B<A` without a measured and explicitly pinned baseline.
- Mutate Pantry, Shopping, RecipeVersion, MealPlan or Serving; reserve/consume inventory; create PreparedBatch, confirmed portions, PantryMovement, leftover/supply stock, or a user-visible action.
- Add migration, DB/UoW, HTTP/API, frontend, PDF, Retail, AI, source publication, new dependency or status provider in A1.

**Suggested future pure interface (outline only, not this PR):**

```text
calculate_prep_diagnostic(
    pinned_meal_plan: MealPlanDetail,
    pinned_recipe_versions: Mapping[RecipeVersionId, RecipeVersionDetail],
    ingredient_form_authority: Mapping[FoodIngredientId, CanonicalFoodFacts],
    policy_version: str
) -> PrepDiagnosticResult(
    source_fingerprint: str,
    event_ingredient_quantities: tuple[SourceBackedIngredientRequirement, ...],
    candidate_step_references: tuple[NonExecutableSourceStepReference, ...],
    unresolved: tuple[PrepUnresolvedDiagnostic, ...],
    executable_tasks: ()  # ALWAYS empty in A1
)
```

This is **not** a new approved public/domain schema or endpoint; concrete types and canonical quantity helpers are determined by the bounded PR10-A1 review. A1 must not reinvent source-of-truth membership/recipe validation or convert Shopping summaries into Prep authority. Existing `MealPlanDetail`, `RecipeVersionDetail` and pure `shopping_calculation` patterns are implementation references. Avoid needless new type dependencies: only introduce those indispensable for the pure result.

**Error semantics:** invalid required Household/MealEvent/Serving/RecipeVersion joins, quantity/unit/form integrity or missing required verified recipe → reject diagnostic calculation with typed error and no partial authoritative output. Valid-but-unreviewed Step/source process → deterministic unresolved result with **zero executable tasks**. Repeated exact immutable inputs produce identical quantity/unresolved/fingerprint; IDs/timestamps unrelated to semantic identity must not influence content fingerprints. There is no persisting success status to blur the distinction.

## 5. Stage C — finished cooked-batch, confirmed inventory and later product value

The user promise remains: *cook a finished dish once → independently establish edible output → divide into individualized confirmed portions → safely chill/freeze/package → retrieve, thaw/reheat where applicable → consume across multiple MealEvents → account for leftovers/waste → feed next-week planning*. Source-backed full recipe, applicable food-safety/time authority, form/yield, equipment capacity, exclusion/portion allocation, real execution confirmation and an immutable PreparedBatch/stock ledger are separate gates. **Planned PrepPlan never equals confirmed stock.** Pantry availability and Shopping aggregation must only use authoritative available supply and known source quantities; missing price/stock/food form/cost remains UNKNOWN.

Before **any real-family/consumer/paid release**, retain independently accepted `SAFE_BATCH_READY`, `PORTION_RELEASE_READY`, technical Gate2, consumer Gate3, data/security/tenant release gates and explicit observability for claimed time/cost/waste/decision savings. Generic Shopping stands alone; future retailer basket handoff and SKU pricing are optional adapters after canonical demand validation and cannot block or silently override core FoodIngredient/Shopping.
