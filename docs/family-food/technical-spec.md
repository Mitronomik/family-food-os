# Техническое задание
## FamilyFoodOS — персональная система планирования питания, закупок и домашних заготовок

**Версия:** 0.1
**Статус:** исходное ТЗ для проектирования MVP
**Формат продукта:** Web / PWA
**Рабочее название:** FamilyFoodOS
**Целевой рынок MVP:** Россия, первоначально Санкт-Петербург

> **Каноническая интерпретация:** это исходное ТЗ сохраняет продуктовые
> требования и исторический контекст. Более поздние принятые архитектурные и
> sequencing-решения поддерживаются в
> `docs/family-food/architecture.md` и
> `docs/family-food/master-roadmap.md` и имеют приоритет там, где это ТЗ
> конфликтует с ними по архитектуре или порядку реализации.

---

# 1. Назначение проекта

FamilyFoodOS — сервис для автоматического планирования питания семьи на неделю с учётом:

- состава семьи;
- возраста членов семьи;
- антропометрических параметров;
- физической активности;
- целей питания;
- пищевых предпочтений;
- исключённых продуктов;
- доступного бюджета;
- времени на приготовление;
- уже имеющихся дома продуктов;
- возможности предварительных заготовок и заморозки;
- стоимости продуктов;
- ассортимента продуктовых магазинов.

Основной результат работы системы — не отдельный рецепт или расчёт калорий, а полностью сформированная **операционная неделя питания семьи**:

**план питания → порции → продукты → закупка → заготовки → приготовление → остатки → обратная связь → следующая неделя.**

---

# 2. Основная продуктовая гипотеза

Пользователь платит не за рецепты и не за доступ к ИИ.

Основная ценность продукта:

> убрать постоянную необходимость самостоятельно решать, что приготовить, сколько продуктов купить, как вписаться в бюджет и что можно приготовить заранее.

Система должна снижать:

- количество импульсивных покупок;
- стоимость продуктовой корзины;
- количество выбрасываемой еды;
- количество ежедневных решений о питании;
- время приготовления еды в рабочие дни.

Одновременно система должна поддерживать:

- разумное разнообразие рациона;
- соответствие базовым нутриционным требованиям;
- индивидуальные размеры порций;
- предпочтения членов семьи;
- возможность использования обычных и доступных в РФ продуктов.

---

# 3. Принцип архитектуры

Ключевой принцип:

> **основная система должна полностью работать без LLM и других генеративных нейросетей.**

ИИ является дополнительным слоем взаимодействия и персонализации.

Без нейросети должны функционировать:

- расчёт пищевой ценности;
- расчёт порций;
- формирование недельного меню;
- проверка ограничений;
- расчёт ингредиентов;
- объединение ингредиентов между рецептами;
- учёт остатков;
- расчёт закупки;
- подбор упаковок;
- расчёт стоимости;
- планирование заготовок;
- расчёт сроков хранения;
- генерация PDF;
- история питания.

Использование AI не должно быть обязательным условием для генерации корректного меню.

# 5. Целевая аудитория MVP

Основной первоначальный сегмент:

женщины примерно 35–45 лет, управляющие питанием семьи.

Однако архитектура продукта не должна содержать жёсткого ограничения по полу или возрасту.

Типичный пользователь:

- семья 2–5 человек;
- есть один или несколько детей;
- продукты покупаются 1–2 раза в неделю;
- пользователь хочет питаться рациональнее;
- не хочет ежедневно придумывать меню;
- хочет экономить;
- хочет покупать продукты по списку;
- использует обычные российские магазины;
- не хочет искать экзотические или дорогие ингредиенты;
- допускает предварительные заготовки;
- активно пользуется смартфоном.

# 6. Основной пользовательский сценарий

## 6.1. Первичная настройка

Пользователь:

1. регистрируется;
2. создаёт домохозяйство;
3. добавляет членов семьи;
4. заполняет параметры каждого человека;
5. указывает пищевые предпочтения;
6. указывает исключённые продукты;
7. задаёт недельный бюджет;
8. задаёт доступное время на готовку;
9. выбирает любимые или доступные магазины;
10. указывает продукты, уже имеющиеся дома.

После этого система должна быть способна самостоятельно сформировать первую неделю.

# 9. Ограничения медицинской функциональности

MVP не является медицинским сервисом.

Сервис не должен:

- ставить диагнозы;
- назначать лечение;
- заменять врача;
- назначать лечебные диеты;
- давать рекомендации по лечению заболеваний;
- рассчитывать терапию.

В MVP допускаются пользовательские ограничения вида:

- не использовать арахис;
- исключить молоко;
- не использовать свинину;
- не использовать грибы.

Предпочтительный интерфейс:

**«Исключённые продукты и ингредиенты»**

вместо хранения медицинских диагнозов.

Специальные медицинские режимы должны рассматриваться как отдельный будущий модуль.

# 15. Система порций

Система должна отделять:

**рецепт**

от

**размера порции конкретного человека.**

Например, одна партия блюда производится на семью, но система рассчитывает разные размеры порций.

Архитектурно:

`Recipe → MealBatch → Serving → HouseholdMember`

Система должна уметь:

- масштабировать рецепт;
- рассчитывать общий объём;
- делить его между участниками;
- обеспечивать различный размер порций;
- учитывать отсутствие конкретного члена семьи на определённом приёме пищи.

# 16. Nutrition Engine

Отдельный детерминированный компонент.

Задачи:

- расчёт энергетической ценности;
- расчёт макронутриентов;

- расчёт дневного рациона;

# 17. Meal Planning Engine

Основной интеллектуальный модуль системы.

Получает:

- состав семьи;
- доступные рецепты;
- пищевые ограничения;
- предпочтения;
- бюджет;
- время;
- историю питания;
- остатки;
- доступные продукты;
- ограничения по повторяемости.

Формирует:

`MealPlan`

для заданного периода.

Для MVP период:

**7 дней.**

---

# 18. Целевая функция планировщика

Необходимо обеспечить возможность оптимизации по нескольким показателям.

Условно:

`Score = Cost + CookingTime + Waste + Complexity + Repetition + PreferencePenalty`

Вес каждого показателя должен настраиваться.

---

# 19. Ограничения планировщика

Примеры:

- недельный бюджет не превышен;
- исключённые продукты отсутствуют;
- число повторов одного блюда ограничено;
- средняя энергетическая ценность соответствует заданному диапазону;
- время приготовления соответствует доступному;
- присутствует минимальное разнообразие;
- определённое число блюд подходит для предварительного приготовления;
- используются остатки;
- минимизируется количество уникальных ингредиентов.

# 20. Режимы планирования

Предусмотреть поддержку пользовательских пресетов.

## Standard

баланс цены, времени и разнообразия.

## Budget

максимальное снижение стоимости.

## Easy Week

минимум готовки.

## Freezer Week

максимальное количество заготовок.

## Pantry Cleanup

максимальное использование имеющихся продуктов.

приоритет разнообразия.

# 21. Shopping Engine

После создания меню система должна:

1. агрегировать ингредиенты всех блюд;
2. суммировать необходимое количество;
3. учитывать съедобную часть;
4. учитывать продукты дома;
5. вычитать доступные остатки;
6. округлять до разумного количества покупки;
7. формировать shopping list.

---

# 24. Использование остатков

Planner должен повышать приоритет рецептов, использующих продукты:

- близкие к окончанию срока хранения;
- уже открытые;

В будущем возможно использование FEFO-подхода.

# 25. Batch Cooking Engine

Отдельный модуль планирования предварительных заготовок.

Результат должен отвечать на вопрос:

> что выгодно приготовить заранее и в каком порядке.

Пример:

**Воскресенье, 1 час 40 минут**

1. поставить вариться бульон;
2. приготовить 1,5 кг фарша;
3. сформировать 8 котлет;
4. сформировать 12 тефтелей;
5. приготовить соус;
6. часть заморозить;
7. часть оставить на ближайшие дни.

# 30. Retail Parser / Connector

Парсеры магазинов должны быть отдельным инфраструктурным слоем.

Пример интерфейса:

```text
RetailConnector

    search_products()
    fetch_product()
    fetch_prices()
    normalize()
```

Каждый магазин реализует собственный connector.

Не допускается смешивание parsing-кода с Shopping Engine.

# 33. SKU Matching

Необходим механизм сопоставления:

`RetailSKU → FoodIngredient`

Пример:

- «Филе грудки цыплёнка»;
- «Грудка куриная охлаждённая»;

- количество упаковок.

`PurchasedQuantity >= RequiredQuantity`.

---

# 37. Задачи AI

Разрешённые сценарии:

### Natural Language Input

Пользователь:

> В среду муж не ужинает дома, детям надоела гречка.

AI превращает запрос в structured changes.

---

### Recipe Replacement

> Замени треску чем-нибудь недорогим.

AI предлагает варианты.

Planner валидирует результат.

---

### Pantry Assistant

> Есть фарш, две морковки и сметана.

AI помогает распознать запрос, но итоговые рецепты проверяются системой.

---

### Feedback Interpretation

> На следующей неделе хочу меньше курицы и вообще попроще.

AI преобразует это в параметры:

- chicken_frequency--;
- cooking_complexity--;
- max_active_time--;

---

### Explanation

AI может объяснять:

- почему выбрано блюдо;
- почему такой объём;
- как сделать замену;
- как использовать остатки.

---

# 38. AI Provider Abstraction

Нельзя жёстко привязывать продукт к одному провайдеру.

Необходим интерфейс вида:

```text
LLMProvider
    complete()
    extract()
    classify()
```

Возможные реализации:

- OpenAI;
- GigaChat;
- локальная модель;
- другие API.

AI Layer должен отключаться feature flag.

---

# 39. Режим без AI

- получить план;
- изменить меню;
- заменить рецепт через UI;
- сформировать покупки;
- работать с остатками;
- получить PDF;
- оставить structured feedback.

Это обязательное acceptance requirement.

# 71. Основные технические риски

## 1. Качество планирования

Самая важная проблема.

Формально правильный рацион может быть бытово неудобен.

Необходим реальный пользовательский feedback.

## 2. Качество исходных рецептов

Ошибочная база создаст ошибочные планы.

## 3. Retail parsing

Страницы магазинов могут изменяться.

Коннекторы необходимо изолировать.

## 4. SKU normalization

Одинаковые продукты имеют разные названия.

## 5. Персонализация

Недостаточно учитывать только КБЖУ.

Необходимо учитывать реальное поведение семьи.

## 6. Scope creep

Высокий риск начать делать слишком много функций до проверки основного цикла.

# 75. Итоговая формулировка продукта

FamilyFoodOS — это не «генератор меню» и не «ИИ-диетолог».

Это:

> **система управления домашним питанием, которая планирует блюда, индивидуальные порции, покупки, бюджет, остатки и заготовки всей семьи как единый процесс.**

Основное ядро продукта является детерминированным.

AI используется как дополнительный conversational и personalization layer.

Розничные каталоги используются как дополнительный pricing и shopping layer.

Такое разделение позволяет сначала создать устойчивый MVP, проверить ценность продукта на реальных семьях и лишь затем увеличивать технологическую сложность.
