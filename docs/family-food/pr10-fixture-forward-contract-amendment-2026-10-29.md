## 4. Two independent real-Planner process evidence; definition of deterministic week

### A — required first, fixture-only reproducibility

1. **Preflight:** approved manifest and immutable `manifest_sha256`, same pinned source/rights/nutrition availability, legitimate Household/member patterns/exclusions and current PlannerConfig. Independently verify the inputs were frozen **before generating outputs**. The initial negative #254 receipt is an adversarial baseline, not an output to accept or relabel.
2. **Run 1 / Run 2:** two **separate Python interpreter processes**, each creates a wholly new disposable SQLite database with the *ordinary accepted migrations and test seed composition*, independently validates exact versioned source/rights and active RecipeVersion/Step lineage, creates its own genuine Household and member pattern selections, then calls **unchanged** `PlannerService.generate_authoritative`. Persist through existing UoW and independently read `MealPlan`, ordered events and Servings via normal repositories. Never import a completed meal plan/serving snapshot as input.
3. **No selection search:** a single predeclared input version gives one candidate week per process, with no loop over random seeds/UUID sequences/dates or post-hoc selection of the first matching pair. If determinism is not native to the current seed, stop and request **another separately authorized test-only identity/seed contract**; even an optional production-facing composition parameter is an architectural change to review, not automatically authorized by this docs gate.
4. **Normalize exact current persisted output:** from all 21 event rows, sorted by `(local_date, position)`, record `local_date, position, role, source_kind, canonical_recipe_code, source_name, source_recipe_id, source_version, source_document_sha256` and current verified RecipeVersion/Step process content identity. For each event attach its exact set of participating `member_ordinal` and **exact finite positive six-place Decimal string** `portion_servings`; sort by ordinal. Check 42 and unique pairs, Household scope, no missing/extra event/date/role, no duplicate member/slot or source mismatch. Exclude generated UUIDs, timestamps, raw DB insertion order, trace duration and other run-local incidental IDs **only from the semantic comparison**; separately retain all real FKs and source pins in each full receipt.
5. **Compare full semantics, not merely shapes:** both processes produce **identical canonical JSON arrays and SHA256** (UTF-8, `ensure_ascii=false, sort_keys=true, separators=(',', ':')`). Compare **every** 21 source-code/role/date/position selection, participant ordinal set and each of 42 Decimal amounts. A shared input manifest SHA alone, the `3/21/42` counts, within-process pure Planner trace or identical *self-declared* checksum do **not** pass. Two independent raw receipts must independently re-hash and match; record versioned `fixture_id`, new week digest and full provenance in a reviewer-accessible repository/CI artifact.
6. **Reviewer freeze AFTER objective success:** only after both genuine runs match can an independent reviewer examine raw receipts, source/rights and verify the exact algorithm, authorize a distinct **new immutable** `PR10_FF_WEEK_REFERENCE_V1` and external SHA pin. Verify a fresh replay/reinstall/restart on the **unchanged** pinned input as regression where necessary. Do not silently refresh the frozen week after any future source/Planner/policy change; create explicit versioned review with invalidation instead.

**A PASS** means `PR10_FF_FIXTURE_REPRODUCIBLE=PASS` **only** (technical Planner evidence). **It does not set** `APPROVED_IMMEDIATE`, D3 trust, Gate2, `SAFE_BATCH_READY` or `PORTION_RELEASE_READY`. No purported new digest or recipe choices exist in this docs PR. If processes differ in any recipe/role/member/Decimal, record **`NO_GO_FORWARD_FIXTURE_UNSTABLE`** and stop.
