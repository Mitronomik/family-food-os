## 3. Proposed typed test-only identity interface (design only, not Python code)

**Not a universal product identity model.** Proposed test fixture contract `PR10_FF_TYPED_ID_POLICY_V1`, limited to a trusted synthetic fixture builder inside a disposable test database. An explicit opt-in adapter returns **`id_for(entity_kind, semantic_key)`**; ordinary production and normal seed code **must continue using `uuid4`** with zero implicit test fallback. The provider must never be selected by reading `AI_ENABLED`, a generic environment variable or a global singleton.

**Example normative key layout, to be reviewed before implementation:**

| Entity kind | Canonical key input and identity review |
| --- | --- |
| `RECIPE` | fixture namespace / `canonical_code`, independent of mutable title |
| `RECIPE_VERSION` | fixture namespace / canonical code / source name / source recipe ID / source version / source document SHA256 / *actual derived version number and predecessor linkage* / immutable reviewed source-process identity |
| `RECIPE_INGREDIENT` | complete typed RecipeVersion key / **ingredient position**, canonical FoodIngredient code and exact source quantity/unit/form as reviewed |
| `RECIPE_STEP` | complete typed RecipeVersion key / **Step position**, whole original instruction SHA256 and stage/process identity; later correction is a distinct version |
| `HOUSEHOLD` and `MEMBER` | fixture namespace + Household *synthetic* stable code; member ordinal 1, 2 or 3 and exact reviewed profile digest |
| FoodIngredient, custom-pattern selection and output Plan/Event/Serving | Explicitly inventoried as per-run UUID bindings; stabilize only where an independent tie/selection witness proves necessary; **never** use old run UUIDs as current domain/source facts |

**Serialization and hash rules:** reject missing/UNKNOWN key fields; normalize Unicode/source codes, exact Decimal strings, positions, source SHA and canonical JSON to UTF-8 with `ensure_ascii=False, sort_keys=True, separators=(',', ':')`; namespace includes `fixture_policy_version` and a **test-only** reviewer-pinned stable namespace string. No secret or current user identity in keys. A single key must always map to a single ID across all nested seed instances and replay; two distinct keys **must not map to the same ID** and cross-kind collisions fail closed. The bound ID must exist with exactly the same source/version/rights/Steps in the real repository; a matching hash in the fixture alone is never authoritative.

**UUID-format constraint and algorithm status:** existing FamilyFoodOS domains require `UUID.version == 4`; raw `uuid5` yields version 5 and is rejected. **The exact proposed deterministic v4-shaped algorithm is now specified in §3.1 for reviewer/owner approval. It is NOT accepted and is not implemented by this PR.** Its output is deliberately predictable and therefore **not a cryptographically random UUID4** suitable for a real user/security identity. No domain UUID validator relaxation or production token generation is permitted. If the algorithm or production-boundary API cannot be approved **as one complete contract**, `NO_GO_TEST_ONLY_ID_SEAM_UNAPPROVED`, not a partial approval followed by another unspecified algorithm.

### 3.1. Exact proposed deterministic v4-shaped ID algorithm — contract approval gate (P1)

**Normative proposal, not authorization to implement:** specify `PR10_FF_TYPED_ID_POLICY_V1` completely **in this review unit**, rather than approving signatures now and deciding their semantics later. An owner approval must explicitly cover *both* this algorithm and the §4 signature surface; rejecting either yields `NO_GO_TEST_ONLY_ID_SEAM_UNAPPROVED`.

1. **Namespace/policy freeze before any fixture output:** `policy = "PR10_FF_TYPED_ID_POLICY_V1"`, `namespace = "familyfoodos/pr10-ff/fixture-only/v1"`, `fixture_id = "PR10_FF_FORWARD_3M_7D_V1"` as proposed immutable test namespace values. A reviewer must externally pin the complete input manifest and this policy before any run. A new dataset/source/fixture revision requires a *new approved fixture_id/policy*; never change a string just to get a convenient week.
2. **Typed logical input envelope:** `{"policy":policy,"namespace":namespace,"fixture_id":fixture_id,"kind":entity_kind,"key":semantic_key_object}`. `kind` is a closed set: `RECIPE`, `RECIPE_VERSION`, `RECIPE_INGREDIENT`, `RECIPE_STEP`, `HOUSEHOLD`, `HOUSEHOLD_MEMBER`, plus **only** subsequently approved kinds. Each `key` follows the schema in §3 above, with the RecipeVersion correction refinement below. No generated DB UUID, creation timestamp, iteration index, Python `hash()`, transient `MealPlan`/Serving result or mutable display name is permitted in the input key.
3. **Canonical key encoding:** strict JSON object with required fields and no additional fields; strings are Unicode **NFC** and must preserve reviewed source/Step text content (no silent trimming/case-folding); canonical source codes use accepted existing catalogue normalization, 64-digit source SHA are lowercase hexadecimal, positions/version numbers/ordinals are positive JSON integers, optional predecessor is explicit JSON `null`. Decimal numeric fields are **finite, exact, non-float** canonical fixed-point strings (`format(value.normalize(), "f")`, except zero canonicalizes to `"0"`); process/Step text is represented by independently verified full-text SHA-256 and position. No NaN, Infinity, `-0`, floats, implicit defaults, unknown field or silently altered rights is admissible. Serialize with `json.dumps(envelope, ensure_ascii=False, sort_keys=True, separators=(",", ":"), allow_nan=False).encode("utf-8")` (no BOM/newline).
4. **Domain separation and UUID bytes:** `digest = SHA256(b"FamilyFoodOS/PR10-FF/typed-id/v1\x00" + canonical_json_bytes)` with **one actual zero byte** at the end of the ASCII prefix (the `\x00` shown here describes its byte value). Take `bytearray(digest[:16])`, set `raw[6] = (raw[6] & 0x0f) | 0x40` and `raw[8] = (raw[8] & 0x3f) | 0x80`. Parse `UUID(bytes=bytes(raw))`. These are the version-4 nibble and RFC 4122 variant bits; explicitly assert `uuid.version == 4`, RFC_4122 variant, stable round-trip and no collision across any `kind/key` in the fixture. A `uuid5`, random `uuid4`, ordering-dependent pseudo-random stream or changed endianness fails policy parity. **These are predictable test-only v4-*shaped* identifiers, not random UUID4 output or security tokens.**
5. **Two golden vectors, non-negotiable for later tests:** assuming the above `fixture_id` and `namespace`, the envelope `{"fixture_id":"PR10_FF_FORWARD_3M_7D_V1","key":{"canonical_code":"SCHOOL2022_54_1R_COD_CUTLET"},"kind":"RECIPE","namespace":"familyfoodos/pr10-ff/fixture-only/v1","policy":"PR10_FF_TYPED_ID_POLICY_V1"}` must yield **`82a8de65-1a14-49a3-bb9b-44a30d54675f`**. The envelope with `kind="HOUSEHOLD_MEMBER"`, `key={"household_key":"pr10-ff-3m-v1","ordinal":1,"profile_sha256":"0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"}` must yield **`a6f0adfa-af9b-4f69-a9dc-cc4220b1c819`**. The second is an **algorithm conformance vector only** (illustrative fake profile digest), *not* an accepted actual member profile or a freeze of a new Planner fixture.
6. **Registry and collisions:** a per-process, per-fixture typed key registry enforces `same (policy,namespace,fixture_id,kind,key) → same UUID`, different keys/kinds → different UUID; it is shared explicitly by all nested seed objects within the disposable DB and is never process-global. Detect an existing database ID carrying a different semantic key, duplicate source/version keys, unexpected replay writes and cross-Household collisions; fail closed before accepted fixture evidence. Record the full input key+computed UUID ledger and actual persisted row binding in each signed-off QA receipt. The digest's finite collision probability does **not** replace runtime collision/identity assertions.
7. **Trust and lifecycle:** SHA-256 and version bits make a deterministic mapping, **not** a signature or source/rights proof. Bind each key to live immutable RecipeVersion/Step, FoodIngredient, rights and correction authority via accepted readers; independently pin the input manifest/namespace in a trusted repo commit. Never expose predictable test IDs to production APIs, regular seed CLIs, authentication/session secrets or real-family records.

**Version-key refinement:** `RECIPE_VERSION.key = {canonical_code, source_record_key, version_number, predecessor_version_key, publication_kind, publication_process_sha256, correction_revision_sha256}`. `source_record_key` is the typed original SourceRecord tuple `(canonical_code, source_name, source_recipe_id, source_version, source_document_sha256)`; `publication_kind` is `ORIGINAL` or `REVIEWED_CORRECTION`. Original v1 uses `predecessor_version_key=null`, `correction_revision_sha256=null`. For DC4-A3 v2, bind the accepted predecessor *semantic key*, the independently pinned correction **artifact's content SHA-256** and new whole-process/ordered-Step fingerprint, not the source record's unchanged SHA alone. `RECIPE_STEP.key` and `RECIPE_INGREDIENT.key` include the complete published-version key plus positive position and reviewed content/form/source values, so v1 and v2 never share a Step UUID accidentally. The **correction artifact Git blob SHA-1** above is a pin of raw bytes; for the proposed key, independently compute SHA-256 of those exact bytes and verify their Git blob first. The algorithm must reject an unreconstructable predecessor key; never invent its UUID.

**Important implementation limit:** the existing `id_factory: Callable[[], UUID]` does **not** receive these typed keys. The v4 algorithm cannot be installed safely by passing a 51-item UUID list or a single generic callback. Adopting it requires the explicit typed service/composition/call-chain amendment in §4; the implementation must be separately authorized after this docs review.

**Version and replay discipline (three separate identities):** The **original SourceRecord** identity is the accepted `(canonical_code, source_name, source_recipe_id, source_version, source_document_sha256)`; it may legitimately remain unchanged during a source-backed process correction. The **published RecipeVersion** identity additionally includes `version_number`, predecessor RecipeVersion *semantic key* (or null for v1) and a publication-specific process/Step fingerprint. A **reviewed correction revision** is a distinct, independently pinned correction artifact/revision (including the approved old→new Step mapping and correction change note). A v2 may share all SourceRecord fields with its v1 while having distinct Steps and a different **published-version identity**. This is not an automatic conflict.

**DC4-A3 legitimate append:** [`_publish_one`](../../backend/app/seed/dc4_a3_russian_step_corrections.py) first validates the frozen original source and **EXACT_REPLAY** predecessor (including prepared authority); if the predecessor is current and no later version exists, it calls `append_trusted_version_in_scope` and requires `successor.version_number = predecessor.version_number + 1` and `created_from_version_id = predecessor_id`, then publishes/validates successor nutrition in the same UoW. The trusted correction artifact is [`data/curation/dc4-a3-russian-step-corrections/corrections.json`](../../data/curation/dc4-a3-russian-step-corrections/corrections.json) with source-pinned Git blob `ec1f8fca9ff8d3c4ac844f6eab0c3411ece54c68`; it declares exactly seven reviewed v2 Step corrections. The existing successor path requires **one exact v2 and `EXACT_REPLAY`**, not another append. This legitimate protocol is preserved; no identity provider may alter its eligibility, metadata or rollback behavior.

**Conflict vs approved revision:** A changed Step/rights/source/nutrition/quantity **under the same published RecipeVersion semantic key or unreviewed correction revision** is a conflict and **NO_GO**. A changed Step on the *same* original SourceRecord is permitted **only** via the independently accepted correction artifact, exact v1 predecessor, v2 append, correct linked `created_from_version_id`, exact trusted prepared nutrition and later exact replay. Any unexpected third version, missing predecessor, changed correction artifact, mismatched old or new Step, altered rights/source, attempted version-key relabeling or conflict-masking fallback is **NO_GO**. Never use the correction artifact as permission to mutate/rewrite an existing RecipeVersion in place.

**Ledger:** retain a per-run, fixture-only key→UUID and inverse UUID→key ledger with entity type, publication/revision, source/rights and predecessor witness. Persist it only as temporary QA evidence, **never** as a new production table or source authority. Replay of identical trusted publication resolves the same existing row without consuming fresh identity; if a builder cannot supply the stable typed key **before** allocating an ID, `NO_GO_TEST_ONLY_ID_SEAM_UNPROVEN` rather than relying on a call-order counter.
